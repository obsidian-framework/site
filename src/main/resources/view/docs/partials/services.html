Service Providers

Service providers are the central place to configure and register services into the DI container at application boot. Use them when you need setup logic — reading environment variables, opening connections, or binding interfaces to implementations.

Creating a provider

Extend ServiceProvider and implement the register() method.

public class AppServiceProvider extends ServiceProvider
{
    @Override
    public void register() {
        // bind, singleton, or any setup logic here
    }
}
Registering your provider

Declare your providers in the .env file as a comma-separated list of fully qualified class names. They are loaded once at boot, in order.

PROVIDERS=com.myapp.providers.AppServiceProvider
Binding an interface to an implementation

Use bind() to tell the container which concrete class to use when a given interface is requested. Useful for swapping implementations between environments.

Example — AppServiceProvider.java
public class AppServiceProvider extends ServiceProvider
{
    @Override
    public void register() {
        if (env("APP_ENV", "production").equals("testing")) {
            bind(MailService.class, FakeMailService.class);
        } else {
            bind(MailService.class, SmtpMailService.class);
        }
    }
}
Inject by interface anywhere
@Controller
public class AuthController extends BaseController
{
    @Inject
    private MailService mail;

    @POST("/register")
    private Object register(Request req, Response res) {
        // resolves SmtpMailService or FakeMailService
        // depending on APP_ENV
        mail.send(req.queryParams("email"), "Welcome!");
        res.redirect("/dashboard");
        return null;
    }
}
Registering a singleton

Use singleton() when your service requires constructor arguments that come from environment variables — something @Service alone cannot handle since it relies on auto-scanning with no-arg or injectable constructors.

The following example is illustrative. Apply this pattern to any third-party client or service that needs configuration at boot — payment gateways, mailers, SMS providers, etc.

AppServiceProvider.java
public class AppServiceProvider extends ServiceProvider
{
    @Override
    public void register() {
        // PaymentGateway needs an API key at construction time.
        // We instantiate it manually and hand it to the container.
        singleton(PaymentGateway.class,
            new PaymentGateway(env("STRIPE_SECRET_KEY", "")));
    }
}
PaymentGateway.java
public class PaymentGateway
{
    private final String apiKey;

    public PaymentGateway(String apiKey) {
        this.apiKey = apiKey;
    }

    public boolean charge(String customerId, int amount) {
        // call Stripe or any payment provider
        return true;
    }
}
Inject into any controller or service
@Controller
public class CheckoutController extends BaseController
{
    @Inject
    private PaymentGateway payments;

    @POST("/checkout")
    private Object charge(Request req, Response res) {
        boolean ok = payments.charge(
            req.queryParams("customer_id"),
            Integer.parseInt(req.queryParams("amount"))
        );
        return render("checkout/result.html", Map.of("success", ok));
    }
}
@Service vs ServiceProvider

Both are entry points into the DI container — but they serve different purposes.

@Service — no configuration needed
// Automatically discovered and registered at boot.
// Use when the class has no external setup.
@Service
public class SsoService
{
    public boolean validate(String token) {
        // validate JWT or external SSO token
    }
}
ServiceProvider — setup logic required
// Use when you need env variables, constructor arguments,
// interface bindings, or any logic before registration.
public class AppServiceProvider extends ServiceProvider
{
    @Override
    public void register() {
        singleton(PaymentGateway.class,
            new PaymentGateway(env("STRIPE_SECRET_KEY", "")));

        bind(MailService.class, SmtpMailService.class);
    }
}
Boot order

Service providers run after the DI container has been populated. This means you can safely override or extend bindings that were auto-discovered by @Service and @Repository.

1. @Repository and @Service classes are scanned and registered
2. ServiceProvider.register() is called          ← your providers run here
3. Web server starts
4. First request is handled
💡 Tip

If a provider throws, the application will not start. This ensures that misconfigured services — wrong API keys, unreachable hosts — are caught immediately at boot rather than silently failing at runtime.
